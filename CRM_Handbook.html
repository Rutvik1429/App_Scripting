What it is

The short version, before any of the machinery.

Quick CRM is a private web app for tracking clients and the calls you owe them. Your team opens one link, signs in with a name and password, and works with clean forms and tables. Behind that link, every record lives as a row in a single Google Sheet that only you can open.

That split is the whole design. Your team never touches the spreadsheet — they can't even open it. They only ever see the web app, which acts as a controlled window onto the data. You keep full spreadsheet access for yourself, which means you can always fix, export, or bulk-edit data directly when you need to.

It does three jobs: keep a client list with contact details, status, priority, and order value; schedule follow-ups against those clients and mark them done; and show a dashboard that counts what's active, what's due today, and what's overdue.

The three layers

Three separate pieces, each with one job. Most confusion comes from mixing them up.

Data

The Google Sheet — your database

The "CRM DATA" spreadsheet, with four tabs. Every client, follow-up, and user is a row here. Nothing else stores data — no hidden database anywhere.

Server

Apps Script — the rules and the gatekeeper

The .gs files. They run on Google's servers, not in anyone's browser. They check who's asking, validate what they typed, read and write sheet rows, and generate IDs. This is the only layer allowed to touch the spreadsheet.

Screen

The web page — what people see

The .html files. Sidebar, tables, forms, buttons, toast messages. It holds no data of its own — it asks the server for everything and draws whatever comes back.

Why it's built this way

The web app is deployed with Execute as: Me. That means when a teammate uses it, the sheet operations run under your Google permissions, not theirs. This is what lets you share the app without ever sharing the spreadsheet — and it's why the app needs its own name-and-password login instead of relying on Google sign-in.

How one action travels

Following a single "Save Client" click from the button to the spreadsheet and back. Every other action follows this same path.

1

The form is read

The browser collects every field into one bundle, then locks the Save button so a double-click can't create the record twice.

JavaScript.html → wireClientModal()
2

The request is sent with your session token

The run() helper automatically attaches your login token as the first argument, so the server always knows who is asking without the browser resending a password.

JavaScript.html → run() and callServer()
3

The server checks the token

Before touching any data, the token is looked up. Unknown or expired token, or an account marked Inactive, and the request stops here.

Auth.gs → requireAuth_()
4

The data is validated and written

Name and phone are checked, a sequential ID like CID-000042 is generated under a lock so two people saving at once can't collide, and the row is appended to the Clients tab.

Clients.gs → createClient() · Validation.gs · Utils.gs → generateId_()
5

The write is forced to commit

SpreadsheetApp.flush() makes Google finish the write before replying. Without it, the very next read can run before the new row is visible.

Clients.gs
6

Everything reloads together

The browser shows a toast, then calls getAppData — one request returning clients, follow-ups, users, and dashboard numbers from a single read, so the counts and the lists can never disagree.

JavaScript.html → handleResult() → refreshAll() · Dashboard.gs → getAppData()

The dropdown option lists, one per column: Statuses, Sources, Industries, Priorities, FollowupTypes, FollowupStatuses, Roles, ActiveInactive. Add a value to the bottom of a column and it becomes selectable in the sheet immediately.

Careful

The dropdown options shown inside the web app's forms are written into Index.html separately. Adding an option to the Settings tab makes it valid in the spreadsheet, but to offer it in the app's own form you also have to add it to Index.html.

Why HTML files hold CSS and JavaScript

Apps Script can't serve separate .css or .js files the way a normal website does. So the styles and scripts each live inside their own HTML file, and include() glues all three together the moment someone opens the page.

Login & security

How the app knows who someone is without using Google sign-in.

Because the app runs under your Google account, Google can't reliably tell the app who a visitor is. So the app maintains its own accounts on the Users tab.

Setting someone up

  1. Add a row on the Users tab: name, email, role, and Status set to Active.
  2. Type a starting password in plain text in the Password column.
  3. Send them the app link and that password.
  4. The first time they sign in, the app replaces the plain password in the sheet with a scrambled version. From then on, the real password exists nowhere — not even you can read it back.

What happens at sign-in

The password they type is scrambled and compared against the stored scramble. On a match, the server issues a random session token, remembers it for six hours, and sends it to the browser — which stores it and attaches it to every later request. The password itself is never stored in the browser and never travels again.

Worth knowing

Sessions last six hours, which is Google's maximum for this kind of temporary storage. After that, people simply sign in again. To remove someone's access immediately, set their Status to Inactive on the Users tab — they're locked out on their very next click.

Rules that will bite you

Every one of these caused a real bug during the build. They're documented here so they only cost time once.

Google Apps Script cannot send dates to the browser

This is the big one. If a response contains even a single date value anywhere inside it, the entire response silently fails and the browser receives nothing — no error, no warning, just empty screens.

This is what made the Clients and Follow-ups lists come back empty for so long, while the login screen and dashboard numbers worked perfectly. Those worked precisely because they contained no dates.

The rule: every date read from a sheet must be converted to plain text before it's sent. toSafeValue_() in Utils.gs does this for everything. Never bypass it.

Saving your code does not publish it

Editing a file and pressing Ctrl+S changes what's in the editor, but the live app keeps running whatever was published last. You must explicitly publish a new snapshot.

The rule: after saving, always go to Deploy → Manage deployments → pencil icon → set Version to New version → Deploy. Skipping the "New version" step silently discards your change.

Delete doesn't delete

Clicking Delete writes Deleted into that row's Status column. The row stays in your spreadsheet, but every part of the app skips it. Nothing is ever truly lost — but a row that looks perfectly normal in the sheet can be invisible in the app.

To restore a client: change that row's Status from Deleted back to New in the sheet. It reappears immediately.

Dropdown rules can reject what the code writes

The Status column only permits New, Contacted, Active, Inactive, and Lost. Since Deleted isn't on that list, the dropdown rejected it and deleting failed. The delete function now clears the dropdown rule on that one cell before writing.

The rule: if code writes a value into a column that has a dropdown, that value must be an allowed option — or the rule has to be cleared first.

Re-running setup wipes your data

setupDatabase() clears each tab before rebuilding it. It's meant to be run exactly once, when the spreadsheet is empty.

The rule: never run it again on a sheet with real data. Duplicate the spreadsheet first if you must.

Everything loads in one request, on purpose

Clients, follow-ups, users, and dashboard numbers all come from a single getAppData() call. When these were separate requests, two of them could read the sheet a moment apart and disagree — the dashboard saying "1 client" while the list showed none.

The rule: keep them together. If you add a new panel, add its data to getAppData() rather than creating another request.

Publishing changes

The exact sequence, every time. Getting this wrong is the single most common reason a fix "doesn't work".

  1. Paste the new code into the matching file in the Apps Script editor. Select all first (Ctrl+A) and replace the whole file rather than editing pieces — partial edits are how mismatched versions happen.
  2. Save with Ctrl+S. Do this for every file you changed, before deploying.
  3. Click Deploy → Manage deployments.
  4. Click the pencil icon on your existing deployment. Don't create a second deployment — you'd get a second link.
  5. Open the Version dropdown and choose New version. This is the step that actually publishes your saved code.
  6. Click Deploy. Your link stays exactly the same.
  7. Reload the app with Ctrl+Shift+R, or open the link in a private window, so nothing cached interferes.
If a change seems to have no effect

Nine times out of ten, step 5 was missed. Redo the sequence and watch the Version dropdown specifically — it must say "New version" before you click Deploy.

Common tasks

The things you'll actually need to do month to month.

Add a teammate

Add a row on the Users tab with their name, email, Role, Status Active, and a starting password. Send them the app link. No deployment needed — they can sign in right away.

Remove someone's access

Set their Status to Inactive on the Users tab. Their next action is blocked and their name disappears from the login list. Their records stay intact.

Reset a forgotten password

Clear that person's Password cell and type a new plain password. They sign in with it once, and it's scrambled again automatically.

Add a new dropdown option

Add it to the bottom of the right column on the Settings tab. To also offer it inside the app's forms, add the same option to the matching <select> in Index.html and redeploy.

Bring back a deleted client

Find the row in the Clients tab and change Status from Deleted to New.

Import a batch of clients

Paste the rows directly into the Clients tab, matching the column order exactly. Give each row a unique Client_ID that continues the existing numbering, and make sure Status isn't blank or set to Deleted.

Symptoms mapped to the causes actually found during the build.

Saving fails on a dropdown column The value isn't an allowed option Add it to the Settings tab, or clear the rule on that cell
Finding the real error

Two places tell you the truth. In the app, the message bar at the bottom of the screen carries the actual error text. In the Apps Script editor, the Executions panel in the left sidebar logs every server call your app has made, including what failed and why.
